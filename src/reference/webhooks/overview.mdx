Mesub posts an event to your endpoints when a subscription changes. This
section is the reference of what is sent. To set an endpoint up and write its
handler, read the [Webhooks guide](../../docs/webhooks.mdx).

## The request

Each delivery is a `POST` to your endpoint, with a JSON body and three headers:

| Header              | What it holds                                                                 |
| ------------------- | ----------------------------------------------------------------------------- |
| `webhook-id`        | The delivery's id: one per event and per endpoint, the same on every retry    |
| `webhook-timestamp` | When this attempt was sent, in Unix seconds                                   |
| `webhook-signature` | `v1,` then the signature of this attempt, in base64. Sometimes two, see below |

Deliveries are signed the [Standard Webhooks](https://www.standardwebhooks.com)
way: an HMAC-SHA256 of `webhook-id.webhook-timestamp.body`, keyed with the
endpoint's signing secret, the part after `whsec_` decoded from base64. The
signature covers the exact bytes sent, so verify the **raw body**.

When you regenerate a secret with an overlap, the old secret keeps signing
beside the new one until the overlap ends. Every attempt in that window carries
two signatures, space separated, the new secret's first:

```text
webhook-signature: v1,<signed with the new secret> v1,<signed with the old secret>
```

Check each `v1,` signature, and accept the delivery when any one matches.
`mesub.webhooks.verify` does both for you.

## Two ids

| Id                   | Names        | Deduplicate on it to                             |
| -------------------- | ------------ | ------------------------------------------------ |
| `id`, in the body    | The event    | Apply each event once, whichever endpoint got it |
| `webhook-id`, header | The delivery | Skip a retry of a delivery you already handled   |

One event sent to two endpoints of a project is two deliveries: the same `id`,
two `webhook-id`s.

## The event object

Every event has the same shape:

```json
{
    "id": "evt_cmg1x0evt0001",
    "object": "event",
    "type": "subscription.renewed",
    "created_at": "2026-01-31T00:01:00.000Z",
    "network": "mainnet-beta",
    "api_version": "2026-10-02",
    "sequence": 4,
    "data": {
        "id": "cmg1x0abc0001",
        "status": "active"
    },
    "detail": {}
}
```

| Field         | What it says                                                                                             |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| `id`          | The event's id, the same in every delivery of it                                                         |
| `object`      | Always `event`                                                                                           |
| `type`        | The event's name                                                                                         |
| `created_at`  | When the event happened: the moment `data` describes                                                     |
| `network`     | The Solana network: `devnet` or `mainnet-beta`                                                           |
| `api_version` | The version `data` and `detail` are written in, as `Mesub-Version` names it                              |
| `sequence`    | Its place among this subscription's events: 1, 2, 3... Absent on some events                             |
| `data`        | The subscription, as [Retrieve a subscription](../subscriptions/retrieve.mdx) answers it, shortened here |
| `detail`      | The event's own fields. Empty on most events                                                             |
| `test`        | `true` on a delivery sent by hand from the dashboard. Absent otherwise                                   |

`data` is the subscription as it stood right after the change that raised the
event, however late the delivery. Events raised by the same change share it:
a last retry that fails raises `subscription.payment_failed` and
`subscription.stopped`, both showing `status: stopped`. `detail` says what each
event is about.

Deliveries can arrive in any order. Apply a subscription's events in the order
of `sequence`, and skip one lower than the last you applied. An event without
`sequence` cannot be placed: read the subscription's state now with
[Retrieve a subscription](../subscriptions/retrieve.mdx) rather than apply its
`data`.

Bodies written before this shape keep the one they were sent in, on a retry or
a resend too: `{ type, created_at, data }`, with `detail` inside `data`, no
`id`, and `data` as it was at the first attempt.

## Events

| Event                                                                  | Sent when                                               |
| ---------------------------------------------------------------------- | ------------------------------------------------------- |
| [`subscription.created`](./subscription-created.mdx)                   | The first payment landed                                |
| [`subscription.renewal_upcoming`](./subscription-renewal-upcoming.mdx) | A renewal is near, and whether it can pay               |
| [`subscription.renewed`](./subscription-renewed.mdx)                   | A period was paid                                       |
| [`subscription.payment_failed`](./subscription-payment-failed.mdx)     | A charge missed                                         |
| [`subscription.stopped`](./subscription-stopped.mdx)                   | Mesub stopped charging after missed payments            |
| [`subscription.cancelled`](./subscription-cancelled.mdx)               | The customer cancelled; access runs to the period's end |
| [`subscription.resumed`](./subscription-resumed.mdx)                   | A cancellation was undone                               |
| [`subscription.ended`](./subscription-ended.mdx)                       | It is over; `data.end_reason` says why                  |
| [`subscription.expired`](./subscription-expired.mdx)                   | A checkout was started and never signed                 |
| [`test`](./test.mdx)                                                   | You sent one from the dashboard                         |

Mesub may add a type later: keep a default branch.

Missed some deliveries? `GET /v1/events` serves the same bodies over the last
30 days, newest first: catch up there.

## Your answer

Answer with a 2xx within 10 seconds. Anything else, a redirect included,
counts as a failure and is retried: after 1 minute, 5 minutes, 30 minutes,
2 hours, then every 12 hours, for about three days in all.
