`hasAccess` is enough to gate a route. Webhooks are for reacting when something
changes: a renewal, a missed payment, a cancellation.

## Set up your endpoint

In the [dashboard](https://mesub.io/dashboard#developers), open **Developers**,
then **Webhooks**, add your URL and pick its events. Put the endpoint's signing
secret in your server's environment:

```bash
MESUB_WEBHOOK_SECRET=whsec_...
```

An endpoint must be a public HTTPS URL. A project can have up to 16.

## Create a handler

Mesub signs each delivery the [Standard Webhooks](https://www.standardwebhooks.com)
way. The signature covers the exact bytes sent, so verify the **raw body**,
never one a JSON parser read and wrote again.

<CodeGroup>

```ts Express
import express from 'express';
import { Mesub, MesubError } from '@mesub/node';

const mesub = new Mesub(); // reads MESUB_API_KEY and MESUB_WEBHOOK_SECRET

// express.raw on this route, before any express.json() reaches it.
app.post(
    '/webhooks/mesub',
    express.raw({ type: 'application/json' }),
    async (req, res, next) => {
        let event;
        try {
            event = await mesub.webhooks.verify(req.body, req.headers);
        } catch (error) {
            if (error instanceof MesubError) return res.status(400).end();
            return next(error); // Express 4 does not catch a throw in an async handler
        }

        if (await alreadyHandled(event.id)) return res.status(200).end();

        switch (event.type) {
            case 'subscription.renewed':
                // event.data is the subscription, event.data.detail what was paid
                break;
            case 'subscription.payment_failed':
                // event.data.detail: reason, retries_left, next_retry_at
                break;
        }
        res.status(200).end();
    },
);
```

```ts Next.js
// app/webhooks/mesub/route.ts
import { MesubError, verifyWebhook } from '@mesub/node';

export async function POST(request: Request) {
    let event;
    try {
        event = await verifyWebhook(await request.text(), request.headers);
    } catch (error) {
        if (error instanceof MesubError) return new Response(null, { status: 400 });
        throw error;
    }

    if (await alreadyHandled(event.id)) return new Response(null, { status: 200 });

    switch (event.type) {
        case 'subscription.renewed':
            break;
        case 'subscription.payment_failed':
            break;
    }
    return new Response(null, { status: 200 });
}
```

```ts NestJS
// main.ts: keep the raw body beside the parsed one.
const app = await NestFactory.create(AppModule, { rawBody: true });

// mesub-webhooks.controller.ts
import {
    BadRequestException,
    Controller,
    HttpCode,
    Post,
    type RawBodyRequest,
    Req,
} from '@nestjs/common';
import type { Request } from 'express';
import { MesubError, verifyWebhook } from '@mesub/node';

@Controller('webhooks/mesub')
export class MesubWebhooksController {
    @Post()
    @HttpCode(200)
    async receive(@Req() req: RawBodyRequest<Request>) {
        let event;
        try {
            event = await verifyWebhook(req.rawBody!, req.headers);
        } catch (error) {
            if (error instanceof MesubError) throw new BadRequestException();
            throw error;
        }

        if (await alreadyHandled(event.id)) return;

        switch (event.type) {
            case 'subscription.renewed':
                break;
            case 'subscription.payment_failed':
                break;
        }
    }
}
```

</CodeGroup>

Answer with a 2xx within 10 seconds, before any slow work of your own. Anything
else, a redirect included, counts as a failure.

## Test your handler

### See a delivery before writing any code

[webhook.site](https://webhook.site) gives you a public URL that shows every
request it receives. It is the quickest way to see what Mesub sends.

1. Open [webhook.site](https://webhook.site) and copy **Your unique URL**.
2. In the [dashboard](https://mesub.io/dashboard#developers), under
   **Developers** then **Webhooks**, add that URL as an endpoint.
3. On that endpoint, click **Send test**.
4. Back on webhook.site, the request appears with its JSON body and three
   headers: `webhook-id`, `webhook-timestamp` and `webhook-signature`.

The signing secret is not in the request. It stays in the dashboard, and your
handler uses it to check `webhook-signature`. Remove the endpoint when you are
done: it would receive your real events too.

### Send a test event to your own handler

In the dashboard, on your endpoint, pick the event to simulate and click
**Send test**. With no event picked, the plain `test` event is sent. A test
delivery is signed like a real one and carries `"test": true` at the top of its
body, with a made-up subscription whose id is `sub_test`, so your handler can
recognise and ignore it.

The endpoint must be enabled, and one test is pending at a time: wait for it
to be delivered before sending the next.

A handler running on your machine needs a public URL. A tunnel such as
[ngrok](https://ngrok.com) gives it one.

## Events

| Event                           | Sent when                                               |
| ------------------------------- | ------------------------------------------------------- |
| `subscription.created`          | The first payment landed                                |
| `subscription.renewal_upcoming` | A renewal is near, and whether it can pay               |
| `subscription.renewed`          | A period was paid                                       |
| `subscription.payment_failed`   | A charge missed                                         |
| `subscription.stopped`          | Mesub stopped charging after missed payments            |
| `subscription.cancelled`        | The customer cancelled; access runs to the period's end |
| `subscription.resumed`          | A cancellation was undone                               |
| `subscription.ended`            | It is over; `data.end_reason` says why                  |
| `subscription.expired`          | A checkout was started and never signed                 |
| `test`                          | You sent one from the dashboard                         |

Mesub may add a type later: keep a default branch. The reference has
[one page per event](../reference/webhooks/overview.mdx), with its payload.

## The event object

Every event has the same shape: its `type`, when it happened (`created_at`),
and `data`, the subscription as `subscriptions.retrieve` answers it, plus
`detail`, which is the event's own. The id to deduplicate on is not in the
body: it is the `webhook-id` header, which the SDK gives you as `event.id`.

## Before a renewal

`subscription.renewal_upcoming` is sent once per period, when a subscription
enters the last quarter of it, and three days before the charge at most:
three days ahead on a monthly plan, six hours on a daily one. Mesub reads the customer's wallet at that moment, and `data.detail` says
what the coming charge would meet:

```json
{
    "can_pay": false,
    "renewal_issue": "balance",
    "amount": "9990000",
    "mint": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v",
    "due_at": "2026-03-02T00:00:00.000Z"
}
```

| Field           | What it holds                                                            |
| --------------- | ------------------------------------------------------------------------ |
| `can_pay`       | Whether the charge would go through as the wallet stood when it was read |
| `renewal_issue` | `balance`, `authority`, or null when it can pay                          |
| `amount`        | What will be charged, in the token's smallest unit                       |
| `mint`          | The token                                                                |
| `due_at`        | When the charge is due                                                   |

`balance` means the wallet holds less than the amount, or has no account for
the token: the customer adds funds. `authority` means Mesub can no longer move
the tokens: the approval was replaced or is too small, or the account is
frozen. Subscribing again gives a new approval.

It is sent whether the charge can pay or not, so it also works as a plain
reminder before a renewal. It is a reading, not a promise: a wallet topped up
or emptied afterwards changes the outcome, and the charge itself answers with
`subscription.renewed` or `subscription.payment_failed`.

An endpoint receives it only if that event is selected for it in the
dashboard: an endpoint created before it existed does not get it by itself. Mesub also mails the customer when the charge cannot pay and the
subscription carries an email.

It is never sent for a charge that cannot happen. A subscription in the last
period of a plan with an end date has no renewal: no event, and no mail.

## At a plan's end

A plan can have an [end date](./lifecycle.mdx#when-the-plan-has-an-end-date),
and three events read differently around it.

| Event                           | What changes                                                           |
| ------------------------------- | ---------------------------------------------------------------------- |
| `subscription.renewal_upcoming` | Not sent in the last period: the plan ends before the next charge      |
| `subscription.payment_failed`   | Can carry `next_retry_at: null` and `retries_left: 0` in `data.detail` |
| `subscription.ended`            | Sent at the plan's end, with `data.end_reason` at `plan_ended`         |

A charge that misses when the plan ends before the next retry has no retry to
announce: `next_retry_at` is null, `retries_left` is 0 and `retry_mode` is
null. The subscription stays `unpaid` until the plan's end, then ends. On
Free, `retry_deadline` is the plan's end when that comes before the deadline.

`subscription.ended` arrives within a few minutes of the plan's end, for a
subscription that was still `active` or `unpaid`. Access has stopped at the
end itself: an event delivered in between can carry `status: "active"` with
`access: false`.

## Delivery behavior

### Retries

If your endpoint does not answer with a 2xx, Mesub tries the same event again:
after 1 minute, 5 minutes, 30 minutes, 2 hours, then every 12 hours, for about
three days in all. Each retry carries the same `event.id` as the first try.

An endpoint that fails for three days with no success in between is disabled.
Fix it, then enable it again in the dashboard.

### Duplicates

The same event can arrive more than once. Store the ids you handled and drop a
repeat.

### Order

Order is not guaranteed: a retry can land after a later event. Before granting
or revoking anything, ask `hasAccess` rather than trusting the last event you
saw.
